promptApi Utility

VERY EXPERIMENTAL: DO NOT RELY ON THIS

Everything here that uses the browser's built-in AI (the Prompt API) is an experiment, and it is not useful yet. The model that ships with Chrome is tiny. In the author's testing it could not answer a single question correctly: it ignored its instructions, skipped tool calls, made up attributes and wrote wrong code. The code around it works (it sends messages, runs tools and shows replies), but do not expect correct answers, and do not put it in front of your users.

It needs a recent desktop Chrome with the on-device model available, and the first message downloads the model. This does not affect the rest of the chat: a chat you connect to a person, a server or a cloud model works as usual.

Description

The promptApi utility wraps the browser's built-in language model (Chrome's Prompt API, the LanguageModel global). Give it the path of a file and that file's text becomes the model's system prompt, the instructions that tell it what its job is. It returns a session that keeps the conversation, so each prompt can build on the ones before it. <k-chat prompt-api> uses it to chat with the model.

Basic Usage

import {
  isSupported,
  getAvailability,
  createSession
} from './utils/promptApi.js';
if (isSupported() && await getAvailability() !== 'unavailable') {
  const session = await createSession({
    path: '/prompts/support-agent.md'
  });
  console.log(await session.prompt('How do I reset my password?'));
  session.destroy();
}

The System Prompt File

Any text file the browser can fetch works, a .md or .txt file next to your pages, for example. Write it as plain instructions to the model: its role, the tone, what to answer and what to refuse. It is loaded once, when the session is created. Pass systemPrompt with a string instead of path to skip the file.

Pass an array of paths and the files are read in order and joined, so the model's job can live in one file and what it should know in others. Keep them short: the browser's model can only read a few thousand tokens, and the system prompt shares that with the conversation. If the files are too big, createSession throws an error saying so.

API Methods

isSupported()

Whether the browser has the Prompt API at all.

Returns: boolean

getAvailability(options?)

Whether the model can be used right now. options.language is the language of the conversation, default 'en'.

Returns: Promise<'unavailable' | 'downloadable' | 'downloading' | 'available'>

loadSystemPrompt(path)

Fetches the file (or each file, when given an array) and returns the trimmed text, with several files joined by a blank line. Throws if a request fails.

Returns: Promise<string>

createSession(options?)

Loads the system prompt and creates a model session. If the model is not downloaded yet this starts the download, which the browser only allows after a user gesture (a click or key press), so call it from an event handler. Throws if the Prompt API is not supported.

options
OptionDescription
path: string | string[]URL of the file holding the system prompt, or an array of URLs whose texts are joined in order
systemPrompt: stringThe system prompt as a string, ignored when path is set
history: ArrayEarlier turns to start from, [{ role: 'user' | 'assistant', content }]. If they do not fit in the model's memory the oldest are left out, two at a time. Use it to continue a conversation saved with conversations
language: stringLanguage code for the input and output. Default 'en'
temperature, topKSampling parameters, passed to the model when set
onDownloadProgress: (loaded) => voidCalled with a number from 0 to 1 while the model downloads
tools: ArrayFunctions the model can call, each { name, description, inputSchema, execute(args) }. See Tools
onLog: (text) => voidCalled with a line of plain text for every step: the system prompt, each message sent to the model, its raw reply, each tool call and its result, and the context used. Use it to see why a small model did what it did

Returns: Promise<Session>

Session

session.prompt(text, { signal }?): Promise<string>

Sends a message and resolves with the whole reply.

session.promptStreaming(text, { signal }?): AsyncGenerator<string>

Sends a message and yields the reply in pieces as it is written. Each piece is new text, not the reply so far, so add them up.

session.destroy()

Ends the session and frees the model. Do this when the conversation is over.

session.systemPrompt: string

The system prompt text the session was created with.

session.inputUsage and session.inputQuota

How much of the model's context the conversation has used, and how much there is in total. The model forgets the oldest messages when it runs out.

Continuing a Conversation

A session only remembers what happened while it was open. To carry on after a reload, save the messages with conversations and give them back as history when you create the next session. <k-chat persistent-id> does exactly this.

import {
  createSession
} from './utils/promptApi.js';
import {
  getConversation
} from './utils/conversations.js';
const {
  messages
} = await getConversation(id);
const session = await createSession({
  path: '/prompts/support-agent.md',
  history: messages.map(m => ({
    role: m.type === 'outgoing' ? 'user' : 'assistant',
    content: m.markdown
  }))
});

Tools

Give the session tools and the model can do things, not just reply. Each tool has a name, a description the model reads to decide when to use it, an inputSchema (JSON Schema) for its arguments, and an execute function. When the model decides to use a tool, the browser calls execute with the arguments, then gives the string it returns back to the model, which carries on with its reply.

This does not use the browser's own tool calling, which Chrome's model did not act on. The tools are described to the model in its system prompt, and it asks for one by writing a line like TOOL_CALL {"name": "setTheme", "arguments": {"theme": "dark"}}. The session hides that line, runs your function, and sends the result back as TOOL_RESULT ..., so prompt() and promptStreaming() only give you the words meant for the user. A small model does not always write the call exactly as asked, so a reply that is only a JSON object naming one of your tools is run as a call too, with or without a code fence (```json, ```tool_call), and with parameters or args instead of arguments. Other JSON, and replies that start with a code fence for code, are shown as the answer. A tool that throws is reported to the model as an error. The model is small, so it can still miss a call or answer without making one: say in your system prompt when each tool should be used.

import {
  createSession
} from './utils/promptApi.js';
import {
  setTheme
} from './utils/theme.js';
const session = await createSession({
  path: ['/prompts/support-agent.md', '/prompts/product-list.md'],
  tools: [{
    name: 'setTheme',
    description: 'Changes the color theme of the page',
    inputSchema: {
      type: 'object',
      properties: {
        theme: {
          type: 'string',
          enum: ['light', 'dark', 'auto']
        }
      },
      required: ['theme']
    },
    execute: ({
      theme
    }) => {
      setTheme(theme);
      return `The theme is now ${theme}.`;
    }
  }]
});
console.log(await session.prompt('Switch to dark mode please'));

Looking Things Up

A tool can also hand the model information, not only do something: whatever it returns goes back to the model, which then answers from it. That lets you keep the system prompt small, in three layers:

  1. A small system prompt that says what the model's job is.
  2. A short overview that lists everything that exists and what each thing is for, in a few words. It does not say how anything works. Write it in terms of what people want to do ("accordion: show/hide content in collapsible sections").
  3. A tool that looks up the details of one thing: a small text file for each component or utility, with its attributes, methods, events and an example.

The plain-text docs of these components and utilities are published next to their pages (for example card.txt and promptApi.txt), with overview.txt listing what each is for. They are the kind of data such a tool would return. In the author's testing the browser's built-in model could not use a setup like this at all: it often did not call the tool, wrote the call wrongly, or ignored the result and made things up. A much bigger model is a different story.

import {
  createSession
} from './utils/promptApi.js';
const components = ['accordion', 'card', 'show-more', 'tabs'];
const session = await createSession({
  // The model's job, and a short overview of what each component is for
  path: ['/prompts/helper.md', '/prompts/overview.txt'],
  tools: [{
    name: 'getComponentDocs',
    description: 'Gets the documentation of one component: its attributes, methods and events.',
    inputSchema: {
      type: 'object',
      properties: {
        name: {
          type: 'string',
          enum: components
        }
      },
      required: ['name']
    },
    execute: async ({
      name
    }) => {
      const response = await fetch(`/docs/components/${name}.txt`);
      return response.ok ? await response.text() : `Error: there is no component named "${name}". Use a name from the overview.`;
    }
  }]
});
// "What attributes does the card take?" -> the model calls getComponentDocs({ name: 'card' }) and answers from the result
console.log(await session.prompt('What attributes does the card take?'));
  • Keep each doc small. The result takes room in the model's context, together with the system prompt, the overview and the conversation. A few hundred words for one component, never a whole docs page.
  • Match names forgivingly: the model might ask for card, k-card or <k-card>. An enum of the names in the tool schema (as in the example) helps a model pick a valid one, but it costs context.
  • Return an error as text when nothing is found, ideally saying where to look (Use a name from the overview.), so the model can try again or say it does not know.
  • Tell the model to use the tool in the system prompt, and to never guess when it has not looked something up.

Editing a Document with Tools

Tools can change something in your app, such as a page builder where the user says "Add a blue button under the content slider" and the model edits the page. The obvious design is to send the model the whole JSON tree of the page and have it send back the changed tree. Don't. Give it small tools and let your own code make the change.

Why not send the whole tree

  • It does not fit. The model reads only a few thousand tokens at once, and that has to hold the system prompt, the conversation and the tree. The JSON of a real page can fill all of it.
  • It gets the tree wrong. A small model that rewrites a large JSON document drops, repeats and corrupts nodes, and the mistakes are hard to notice. A call that adds one widget is easy for it to get right, and easy for you to check.

What to do instead

  1. One tool per kind of change. addWidget, updateWidget, moveWidget, removeWidget, each with a small inputSchema. "Add a blue button under the content slider" becomes addWidget({ type: 'button', props: { color: 'blue' }, afterId: 'w7' }). Use enum in the schema for anything with a fixed set of values, such as the widget types.
  2. A short outline, not the JSON. Give the model a getPageOutline tool that returns one line per widget with its id, type and label, indented by nesting (w7 content-slider "Hero slides"). That is enough to find "the content slider" and to use its id, and it is a fraction of the size of the tree.
  3. Describe the widgets in a file. A short list of the widget types and the props each takes goes in a system prompt file, next to the file that says what the model's job is. See several files.
  4. Check everything in execute. The model will make up ids and types. Check that the type, the id and the props exist, and if not return a short error such as Error: there is no widget "w99". The session gives it back to the model, which can try again. Do not throw for these, and do not trust the arguments.
  5. Make the change with your app's own commands. Call the same code that drag and drop calls, so undo and redo, selection and saving keep working. Return what happened (Added w12.) so the model can refer to the new widget.
import {
  createSession
} from './utils/promptApi.js';
// `builder` is your app: its widget tree, a catalog of widget types, and the same
// commands that drag and drop uses (so undo and redo keep working).
const outline = (widget, depth = 0) => ['  '.repeat(depth) + [widget.id, widget.type, widget.label && `"${widget.label}"`].filter(Boolean).join(' '), ...(widget.children || []).map(child => outline(child, depth + 1))].join('\n');
const session = await createSession({
  path: ['/prompts/page-builder.md', '/prompts/widget-catalog.md'],
  tools: [{
    name: 'getPageOutline',
    description: 'Lists the widgets on the page, one per line, indented by nesting, as: id type "label".',
    inputSchema: {
      type: 'object',
      properties: {}
    },
    execute: () => outline(builder.tree)
  }, {
    name: 'addWidget',
    description: 'Adds a widget. afterId is the widget it goes directly after. Use parentId instead to put it first inside a container.',
    inputSchema: {
      type: 'object',
      properties: {
        type: {
          type: 'string',
          enum: Object.keys(builder.catalog)
        },
        props: {
          type: 'object'
        },
        parentId: {
          type: 'string'
        },
        afterId: {
          type: 'string'
        }
      },
      required: ['type']
    },
    execute: ({
      type,
      props = {},
      parentId,
      afterId
    }) => {
      if (!builder.catalog[type]) return `Error: there is no widget type "${type}".`;
      if (afterId && !builder.find(afterId)) return `Error: there is no widget "${afterId}".`;
      return `Added ${builder.add({ type, props, parentId, afterId }).id}.`;
    }
  }]
});
await session.prompt('Add a blue button under the content slider');

The system prompt files

Tell the model it cannot see the page, to ask for the outline, and that the outline goes stale. Everything the model learned from an outline is old after the next edit, and it will not notice unless you say so.

You edit a web page for the user by calling tools. You cannot see the page: call getPageOutline first to see its widgets and their ids.

- The outline changes after every edit. Call getPageOutline again at the start of each new request.
- Use the ids from the outline. Never make up an id.
- Make one change per tool call. For a request that needs several changes, call the tools one after another.
- If a tool answers with an error, read it and try again with the corrected arguments.
- When you are done, say in one short sentence what you changed.
 
Widget types and their props:

- button: label (text), color (blue, red, green, gray), size (small, medium, large)
- text: content (text), align (left, center, right)
- image: src (url), alt (text)
- content-slider: slides (list of widget ids)

Things to keep in mind

  • The context fills up. Each outline the model asks for stays in the conversation. On a big page with a long conversation, start a new session now and then (newConversation() on a <k-chat>). Once the model's context is full it starts to forget the oldest turns, and you want it to forget the old outlines before it forgets its instructions. Check session.inputUsage against session.inputQuota if you need to know how close you are.
  • Saved conversations do not keep tool results. <k-chat persistent-id> saves only what the user and the model wrote, so after a reload the model has no outline and must ask for it again. That is what you want, as the page may have changed.
  • Simple requests work best. One change per request, such as adding a button, changing a color or moving a widget, is realistic for a model this size. A request that needs many changes ("rebuild the footer with three columns") will often be half done. Test with the real model early, because how well it follows the call format depends on its version.
  • Tell the user what changed. Listen for the tool-call event of the chat to highlight the widget that was added or changed.
